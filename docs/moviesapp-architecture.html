01 · System topology

Two front ends, one API, and one working edge

The repository contains three deployable applications. They share a language and a deployment pipeline, not a contract. The Angular client renders from an in-memory service and never opens an HTTP connection. The MVC app is the only consumer of the API, and its requests do not match the API's routes, identifiers, or authentication.

The mismatch is concrete: the MVC client calls movies against a base URL of /api/, while the API exposes /api/v1/Movie. It sends and expects integer IDs, while the API uses GUIDs. It sends no bearer token, while every movie endpoint requires one.

What the split actually buys

The monorepo centralizes CI filters, container builds, documentation, and security scanning. It does not force a shared domain model, a shared API client, or a shared release cadence. Those remain separate decisions, and today they have been made separately in each app.

03 · API core

The API is where the architecture is enforced

The Web API is split into three projects with one-way project references. The presentation layer composes the other two, and the data layer owns every EF Core dependency. The main caveat is in the domain: ApplicationUser inherits from IdentityUser, so the domain project references the Identity EF Core package.

Request pipeline

Registered order in Program.cs:

1Security headers → 2Exception handling → 3Rate limiting → 4Audit logging → CORS → HTTPS → AuthN → AuthZ → Controllers

100 requests/min for reads, 10 for writes, keyed by user or IP. Failures become RFC 7807 ProblemDetails with a trace ID.

Authentication flow

login → access JWT · 15 min + refresh · 7 days → refresh rotates → old token consumed

Refresh tokens are single-use and bound to the access token's jti. Reuse is rejected, which closes the replay window.

Authorization is layered, not just declared

  • Authentication: every movie endpoint requires a valid JWT.
  • Policy: UserOnly for self-service, AdminOnly for elevated access.
  • Ownership: the repository filters and verifies OwnerId before returning a movie.
  • Input shape: separate create and update DTOs prevent over-posting.
  • Audit: mutations record user, action, entity, IP, user agent, and redacted values.

The strongest architectural decision in the repository is that ownership is enforced in the data layer with dedicated query methods, not left to each controller. A new endpoint has to opt out of that pattern explicitly.

04 · Data model

A small relational model with identity at the center

SQLite holds seven application tables plus the ASP.NET Identity tables. Movies belong to users, and media types and genres attach through explicit junction entities. Refresh tokens and audit records also hang off the user.

Persistence detail worth knowing: startup calls Database.EnsureCreated() even though EF Core migrations are checked in under MoviesApiData/Migrations. A fresh database gets the current model; an existing database is never migrated. The two mechanisms do not compose.

05 · Client state

NgRx is wired correctly; the I/O boundary is still fake

The Angular client follows the conventional unidirectional loop. Components dispatch actions, reducers produce state, selectors feed templates, and effects own side effects. The only side effect implemented today is an in-memory service, so the HTTP seam is the service implementation rather than the components.

SSR path

Express server → AngularNodeAppEngine → prerendered route → hydrated in browser

RenderMode.Prerender covers **. The Express server also exposes /health and serves the browser bundle with a one-year max age.

06 · Delivery

Containers and CI are mature; the documented claims lag the code

Each app builds into a multi-stage image that runs as a non-root user and exposes a health endpoint. Compose wires the API and MVC together. GitHub Actions uses path filters so a docs-only change does not rebuild all three apps.

Runtime shape

  • Angular: Node 24 image, port 4000, non-root, /health.
  • MVC: ASP.NET 10 runtime, port 8080, depends on a healthy API.
  • API: ASP.NET 10 runtime, port 8080, SQLite file created at runtime.
  • Compose: three services on host ports 4000, 8080, and 8081.

Automation

  • Security: runs on push, pull request, weekly schedule, and manual dispatch.
  • Validation, images, release: manual dispatch only.
  • Change detection: per-app filters plus a shared scope.
  • Secrets: pre-commit hooks and gitleaks config are present.

07 · Assessment

A strong API inside an unconnected system

The API has real architectural discipline: enforced layering, ownership checks in the repository, token rotation, redacted audit records, and a middleware pipeline that runs in a deliberate order. The Angular app has a clean state architecture and a well-placed service seam. The MVC app is a legacy surface that has not been brought onto the current contract.

Strengths

  • Layering is enforced by project references, not convention alone.
  • Object-level ownership is a repository concern with dedicated query methods.
  • Security controls are implemented in code and covered by focused tests.
  • NgRx state, effects, and selectors are idiomatic and independently tested.
  • Every app is containerized, health-checked, and path-scoped in CI.

Risks to address

P0

No shared contract between the three Movie models

GUID versus integer IDs, different field sets, different route paths, and no generated client. Any integration work starts by reconciling three definitions by hand.

P0

The only integration edge does not work

MVC calls /api/movies with integer IDs and no bearer token. The API exposes /api/v1/Movie, uses GUIDs, and requires authentication.

P1

Single-instance architecture by construction

SQLite on a local file plus in-memory rate limiting means more than one API replica would split both state and limits. This is fine for a demo and blocks horizontal scaling.

P1

Database initialization does not use migrations

EnsureCreated() builds a fresh schema from the model and ignores the checked-in migrations. Existing databases never receive schema changes.

P2

Duplicate mutation auditing

Controllers write audit records and the audit middleware writes again for the same request. Pick one source of truth before audit volume becomes a problem.

Recommended sequence

P0

Make the API contract the boundary

Treat the OpenAPI document as the source of truth, generate a typed Angular client from it, and use the same document to align or retire MVC.

P1

Wire Angular to the live API

Replace the in-memory MovieService with HttpClient, add an auth interceptor and route guard, and change the client model to GUID IDs and the API's field names. The store and components need no structural change.

P1

Decide MVC's future explicitly

Either rebuild it against the v1 contract with authentication, or mark it as a legacy demo and remove it from the compose and CI critical path.

P2

Harden the delivery path

Run validation on pull requests, supply the JWT secret in compose or document the required environment, untrack the database and Azure files, and switch startup to migrations.

The architecture in one sentence: a production-grade ASP.NET Core API and a modern Angular shell, connected by a Razor app that still speaks the old contract.

08 · Target architecture

Collapse to one client, one API, one contract

The simpler target removes redundancy without removing capability. Angular stays as the single front end, the API becomes one project with folders instead of three projects, and an OpenAPI document becomes the only shared definition of a movie. The Razor MVC surface is the one thing lost, and it is the cheapest thing to give up for a collection app.

−1 application −2 Movie models −1 token type −1 database init path −1 CORS list

Keep, drop, replace

Decision Current Target Why
Front ends Angular and MVC Angular only One client, one auth story, one deployment surface.
API projects Domain + Data + Api One Movies.Api with folders The three-project split costs more than this domain justifies.
Contract Three Movie models OpenAPI + generated client Contract drift disappears by construction.
Client state NgRx store and effects Signals + service layer One collection does not need a store.
Auth JWT + refresh tokens in JS HttpOnly cookie session + antiforgery Same origin makes it simpler and safer.
Data SQLite PostgreSQL, or SQLite with one replica Removes the single-writer scaling constraint.
DB init EnsureCreated() + migrations Migrate() only One mechanism, and schema changes apply.
Rate limiting Custom middleware Built-in ASP.NET Core limiter Less code for the same behavior.
Audit Controllers + middleware One SaveChanges interceptor or one service One record per mutation.
CORS Configured origin list None Same origin through a reverse proxy.

Migration order

  1. Freeze the contract. Write the OpenAPI document from the API's current v1 surface, reduce it to one Movie schema, and generate the TypeScript client from it.
  2. Wire Angular to the API. Replace the in-memory service with the generated client, add cookie or token handling, and change the model to GUID IDs.
  3. Remove MVC. Delete it from docker-compose.yml, the CI filters, and the docs. This is the single biggest reduction in moving parts.
  4. Collapse the API. Merge the domain and data projects into Movies.Api, switch startup to migrations, replace the custom rate limiter, and pick one audit path.
  5. Switch the database if you need more than one replica. Otherwise keep SQLite and document the single-replica constraint honestly.

The one judgment call. If you need Razor pages or a non-JavaScript surface, keep MVC and drop Angular instead. The simplification is in having one front end, not in which framework wins.
